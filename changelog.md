- Geofence restore after a reboot (`LocationManagerCore.setMonitoringRegions`, fixes [#77](https://github.com/Woosmap/geofencing-core-android-sdk/issues/77), mirrors enterprise [#178](https://github.com/Woosmap/geofencing-enterprise-android-sdk/issues/178)): the centre was built as `LatLng(lng, lat)`, so every restored geofence landed on the wrong side of the world and Android could never fire it; the arguments are now `(lat, lng)`. The adds now wait for the removal task to complete instead of racing it. Only circular rows are registered (an isochrone's `radius` is a travel time in seconds), at most 100 per app (regions the device is inside first, then the nearest to the last known position, or the most recently touched when no position is stored), in one request. Regions left out by the cap, or refused by Android as too many, are deleted from the `regions` table so it only claims geofences Android actually holds (when Android refuses the whole set for another reason the rows are kept for the next attempt). The method now waits for the Play Services calls, must run off the main thread (the reboot job already does), and returns `boolean`: `true` when the removal succeeded and every circular row is registered. `LocationManagerProvider.setMonitoringRegions()` changes from `void` to `boolean`, a source-incompatible change for subclasses. Integrators relying on native background geofence events after a reboot will start receiving them.
