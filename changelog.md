- Region logs of native geofence transitions (`PositionsManagerCore.didEventRegionHelper`, fixes [#85](https://github.com/Woosmap/geofencing-core-android-sdk/issues/85)):
  - The log's `dateTime` is now the time the transition was handled. It was copied from the region's previous state change, so an exit carried the time of the enter and a first enter the time the region was created. `saveRegionLogInDataBase` stamps the current time for the same reason.
  - A transition that reports a state the SDK already holds no longer writes a `RegionLog` or touches the region's dwell record or `dateTime`. It used to insert a row without calling `RegionLogReadyListener`, so the `region_logs` table could hold events the host never received, including an exit for a region never entered.
- Geofence restore after a reboot (`LocationManagerCore.setMonitoringRegions`, fixes [#77](https://github.com/Woosmap/geofencing-core-android-sdk/issues/77), mirrors enterprise [#178](https://github.com/Woosmap/geofencing-enterprise-android-sdk/issues/178)):
  - The centre was built as `LatLng(lng, lat)`, so every restored geofence landed on the wrong side of the world and Android could never fire it; the arguments are now `(lat, lng)`. Integrators relying on native background geofence events after a reboot will start receiving them.
  - The adds now wait for the removal task to complete instead of racing it.
  - Only circular rows are registered (an isochrone's `radius` is a travel time in seconds), at most 100 per app: regions the device is inside first, then the nearest to the last known position, or the most recently touched when no position is stored. They are sent in one request; when Android answers "too many" they are added one at a time in that order until Android refuses.
  - Rows left out by the SDK's own 100 cap are deleted from the `regions` table and named in the log. Rows Android refuses as too many (the host app's own geofences count too) are kept for the next restore, as are all rows when Android refuses the whole set for another reason.
  - The method waits for the Play Services calls, is bounded to 5 minutes overall, must run off the main thread (the reboot job already does), and returns `boolean`: `true` when the removal succeeded and every circular row is registered.
  - `LocationManagerProvider.setMonitoringRegions()` changes from `void` to `boolean`, a source-incompatible change for subclasses.
- CI Workflow change: Pin action versions and add Dependabot cooldown
